第 0 章 · 结论速查

一句话：给某道工序在 NX 里加一个 UDE 开关（add_variable = Active），
这道工序输出的每个 X / Y 就从 X1.2 变成 X[1.2+#646]；
工序一结束开关自动关掉，后面没加事件的工序逐字不变。

问题 答案
加在哪 工序的开始事件里加 UDE add_variable，状态 Active
变成什么样 X1.2 → X[1.2+#646]；Y3.4 → Y[3.4+#647]（Z、I/J/K、R、F 一律不动）
变量号怎么来 默认 X = 600+刀号*5-4、Y = 600+刀号*5-3（T10 → #646/#647）
代码在哪 .tcl 里 4 段：事件入口 / 开关函数 / 输出前改写 / 工序结束复位
要不要动 .def 不要。本方案一个字节都不碰 .def
什么时候失效 每道工序结束时由 PB_CMD_collect_cutting_time 自动复位
怎么验收 加事件的工序有方括号，没加的工序与改动前逐字一致

四处改动位置一览：

# 文件 proc 明文行号 作用
1 .tcl MOM_add_variable 782–785 事件入口（NX 一遇到这个 UDE 就调它）
2 .tcl PB_CMD_add_variable_flag 5802–5840 读事件状态 → 打开本工序的开关
3 .tcl PB_CMD_before_output 的 B 段 5973–6008 每行落盘前改写 X/Y
4 .tcl PB_CMD_collect_cutting_time 末尾 6382–6384 工序结束 → 关开关
附 .pui Control Functions 表 777 把 add_variable 事件登记给 proc（不做 = 事件被静默丢弃）

第 1 章 · 为什么要加这个变量号

1.1 问题的起点：坐标是"死数"

后处理吐出来的坐标，原本都是写死的数值：

G0 X111.5 Y0.0 Z62.
G1 X84.9138 Y15.7205 F141.48

这个 111.5 是出程序那一刻从模型上算出来的。以后只要工件在机床上的位置和出程序时不一样
（夹具换了一套、工件在转台上重新装夹、找正后差了几丝、托盘/工位换了），
坐标就得重新算、程序就得重新出、工件号就得重新对。

1.2 加变量号之后：数值 + 宏变量

FANUC 允许在地址后面直接用表达式（[...] 是宏程序的表达式括号），于是可以写成：

G0 X[111.5+#646] Y[0.0+#647] Z62.
G1 X[84.9138+#646] Y[15.7205+#647] F141.48

机床执行时，实际落点 = 后处理算出来的基准值 + #646 里当时的值。
#646 是公共宏变量（#500 以上断电保持），可以在机床侧随时改：

  • 在 MDI / 程序开头用 #646=-0.03 写进去；
  • 由机床的自动测量 / 找正程序写进去；
  • 由上料工在操作面板上手动改。

结果：偏移量变了，NC 程序一个字都不用改、不用重出。
这是这套写法唯一的目的 —— 把"必须重新出程序才能改的量"，变成"机床上改一个变量就能改的量"。

1.3 为什么是"每把刀一组"

这台后处理的 #6xx 区早就按"每把刀占 5 格"分配好了，不是为需求③新开的区：

寿命变量编号 = 600 + 刀号*5（.tcl 第 9194 行注释，寿命段代码）

以 T10 为例，5 格是 #646 ~ #650：

槽位 T10 的变量 用途 谁写的
5N-4 #646 X 坐标偏移 需求③（本文）
5N-3 #647 Y 坐标偏移 需求③（本文）
5N-2 #648 H 调正量（长度方向） PB_CMD_custom_command_10，注释原文 (H TIAO ZHENG BIAN LIANG:#648)
5N-1 #649 D 调正量（半径方向） 同上，(D TIAO ZHENG BIAN LIANG:#649)
5N #650 寿命计数（GOTO 判断用） 寿命段 #650=#650+1

也就是说：5N-2 / 5N-1 原来是"换刀临时变量"，已经被挪走了，5N-4 / 5N-3 是空出来的两格，
坐标偏移正好落在这一组的头上。所以公式才是 600 + 刀号*5 - 4（X）和 - 3（Y）。

一句话：不是"随便找个变量"，而是"塞进这套后处理已经约定好的、每刀一组的槽位里"。
好处是：每把刀可以有自己的 X/Y 偏移（不同刀具装夹位置/主轴不同，偏差本来就不一样），
而且和 H/D 调正量、寿命计数互不打架。

1.4 为什么要"逐工序开关"

同样的 X 字，在这个后处理里还兼职干别的活（.def 里 90 个块含 X/Y）：

行 X/Y 是 能不能加变量号
G53 G0 X0. Y0. 机床坐标 ❌ 加了就撞
G28 / G30 回参考点中间点 ❌
G52 / G92 / G10 局部坐标 / 坐标设定 / 数据输入 ❌
G4 X1.0 X 是时间（秒） ❌
G68 / G68.2 旋转中心 / 倾斜面 ❌
G0/G1/G2/G3、G8x 工件坐标 ✅ 只有这些该加

所以做法必须是"按需开"：
需要偏移的工序加事件，其它工序一个字不动，改造零回归风险。

1.5 适用 / 不适用

适用 不适用（本方案的跳过名单，实测均不被改写）
直线/快速/圆弧：G0 G1 G2 G3 G53 / G53.1 机床坐标
全部循环：G8x（钻/镗/攻/铰） G28 / G30 回参考点
只有 X / 只有 Y 的行 G52 / G92 / G10 坐标类
模态省略 G 的裸坐标行（X1.2 Y3.4） G4 / G04 延时（X 是时间）
G68 / G68.2 / G68.5 旋转/倾斜
含 ( ) 的注释行、操作者信息行
#650=#650+1、IF [#650 GT 37] GOTO 101 等宏变量行（本来就不含裸 X/Y，天然不动）

已知未拦：G65 P.. X.. Y..（宏调用传参）不在跳过名单里 → 实测会被改写。
本机程序若用到 G65 传参，需要在第 3.3 节的跳过规则里补 |65。目前没用，先记着。

第 2 章 · 加变量号的方法是什么

2.1 整体手法：两件事咬合

   ①  UDE 事件  →  打开本工序的"开关"（一个全局变量）
   ②  输出钩子  →  开关开着，就把即将落盘的那一行文本改写

关键在于改哪一层。PB 在每一行 NC 落盘之前留了一个官方钩子：

  • MOM_before_output（.tcl 第 123 行的注释原文）：

    This command is executed just before every NC block is to be output to a file.
    - Never overload this command! - Any customization should be done in PB_CMD_before_output!

  • PB_CMD_before_output（第 5931 行）的职责：

    allows users to massage the NC data (mom_o_buffer) before it finally gets output

    • No need to attach this command to any event marker.

也就是说：每一个 NC 块都会经过它，不用挂任何事件，拿到的就是"已经拼好的整行文本"
（G0 X1.2 Y3.4 的字面内容，小数点、前导零都是后处理算好的写法）。

于是做法变成：不动 .def 的块定义，只改这一行的文本。

2.2 数据流（一次工序的完整时序）

工序开始序列
   └─ UDE: add_variable = Active
         └─ MOM_add_variable          （.tcl 782）
               └─ PB_CMD_add_variable_flag   （.tcl 5802）
                     ├─ 读 mom_command_status → "ACTIVE"
                     ├─ set ::nc_addvar_on 1        ← 开关打开
                     ├─ 读 mom_x_var / mom_y_var → ::nc_x_var / ::nc_y_var（可选）
                     └─ 只影响本道工序

工序内每一个 NC 块（快速/直线/圆弧/循环…）
   └─ 拼好一行 → MOM_before_output → PB_CMD_before_output（.tcl 5931）
         ├─ A 段：循环 R 值跟踪（需求②，与本需求无关）
         └─ B 段：开关 == 1 ? 改写 X/Y : return   ← 本文主角
               X1.2 → X[1.2+#646]

工序结束序列（Operation End Sequence）
   └─ {End of Path} 的第一项 = PB_CMD_collect_cutting_time（.tcl 6334）
         └─ 末尾：set ::nc_addvar_on 0        ← 开关关闭

下一道工序（若没加事件）→ 开关是 0 → 输出逐字不变

2.3 要动哪些文件（清单）

文件 动不动 动什么
.tcl 要动 4 段代码（第 3 章全文）。这是唯一必须改的文件
.pui 已登记 777 行：{add_variable} {PB_CMD_add_variable_flag} {add_variable} {UDE}。不登记，事件会被静默丢弃

.def 不动 本方案一个字节都不碰。桌面的 mill_intergrex_300_2022_EXPR.def 是旧方案（修订4）的产物，别用

所以事件框里看不到"变量号"输入格 —— 现在走的是默认公式。

2.4 操作步骤（NX 里怎么用）

  1. 打开工序（操作导航器 → 双击工序）；
  2. 找到开始事件那一栏 —— 与加 set_new_tool、set_tool_life 的位置完全一样；
  3. 添加 UDE → 选 add_variable → 状态选 Active → 确定；
  4. 出程序，检查这道工序的 G0/G1/G2/G3 和 G8x 是不是 X[..+#646] Y[..+#647]；
  5. 换一道没加事件的工序，检查它的输出必须与改动前逐字一致。

2.5 为什么不采用另外两种做法（都试过）

做法 结果
A. .def 里每条坐标拆成两个字（X_wrap 表达式 + X 数值），用 \opt 互斥 能用，但要在 .def 里改 140 行、新增 2 个地址；且"模态省略重复坐标"会变成按字符串比较，容易出新问题。→ 保留作参考，不采用（这就是修订 4 + _EXPR.def）
B. 块里同放两个 X，用 MOM_suppress once X 屏蔽一个 不成立。① once 只管一个块，循环事件一次出好几个块 → 会出两份坐标；② MOM_disable_address X 是全局开关，会把 G53/G28/G30/G4 里的 X 一起干掉（回零段变 G28 G91）。
C. 改即将落盘的那一行文本（本文采用） 只改1 个 proc；循环多块天然覆盖；不株连；数字格式沿用后处理已算好的写法，逐字一致；最坏失败模式也只是"没改写"，程序照样能跑

一句话对比：

对比项 A/B C（本方案）
要改的地方 .def 140 行 + 多个事件表 1 个 proc 的 B 段
循环多块 覆盖不到 / 出两份 天然覆盖
G53/G28 株连 会 按 G 代码规则跳过
数字格式 要自己 format，容易不一致 沿用原文本，零差异
最坏结果 X 整字消失 最多"没改写"

3.1 事件入口（.tcl 第 782–785 行）

proc MOM_add_variable { } {

}

说明：MOM_<事件名> 是 PB 的约定 —— .pui 里登记了 add_variable → PB_CMD_add_variable_flag，

3.2 开关函数（.tcl 第 5802–5840 行，函数名 PB_CMD_add_variable_flag）

proc PB_CMD_add_variable_flag { } {
#=============================================================
#=============================================================
# 【需求③】工序"开始事件"里加了 UDE "add_variable" 且状态为 Active 时，
#           只对【本道工序】打开坐标宏开关；工序结束时由
#           PB_CMD_collect_cutting_time 自动关闭。
#   注意：NX 送进来的状态值是全大写 ACTIVE，所以做大小写无关判断。
#   事件里可填 x_var / y_var 指定宏变量号；填 0 或不填则用默认公式：
#       X -> #600 + 刀号*5 - 4        Y -> #600 + 刀号*5 - 3
#=============================================================
   global mom_command_status
   global mom_x_var mom_y_var

   set st ""
   if { [info exists mom_command_status] } {
      set st [string tolower [string trim $mom_command_status]]
   }

   set ::nc_addvar_on 0
   set ::nc_x_var 0
   set ::nc_y_var 0

   if { [lsearch -exact {"" inactive off no false disable disabled none} $st] < 0 } {

      set ::nc_addvar_on 1

      set v 0
      if { [info exists mom_x_var] } { regexp {[0-9]+} $mom_x_var v }
      if { $v > 0 } { set ::nc_x_var $v }

      set v 0
      if { [info exists mom_y_var] } { regexp {[0-9]+} $mom_y_var v }
      if { $v > 0 } { set ::nc_y_var $v }
   }

   if { [info exists ::nc_dbg] && $::nc_dbg == 1 } {
      MOM_output_literal "(DBGADD on=$::nc_addvar_on x=$::nc_x_var y=$::nc_y_var)"
   }
}

第 4 章 · 主要代码逐行解释

4.1 MOM_add_variable（事件入口）

proc MOM_add_variable { } {          ;# NX 在工序里遇到 add_variable 这个 UDE 时调用的入口
   PB_CMD_add_variable_flag          ;# 唯一动作：转交给开关函数
}
行 起什么作用 有什么用
proc MOM_add_variable { } 按 PB 命名规则生成的事件入口（MOM_ + 事件名） NX 处理到"工序开始序列里的这个 UDE"时，会自动调到它。入口不写，事件就是空转
PB_CMD_add_variable_flag 转调开关函数 把"事件识别"和"具体逻辑"分开：入口永远只有一行，逻辑全在 PB_CMD_* 里，好维护

4.2 PB_CMD_add_variable_flag（读状态 → 开开关）

行号 代码 起什么作用 有什么用 / 为什么这么写
5812 global mom_command_status 声明要读 NX 送进来的事件状态 这是 UDE 里那个下拉框（Active/Inactive）的值
5813 global mom_x_var mom_y_var 声明可选的手填变量号 事件里填了才会有；没填这两个变量根本不存在，后面靠 info exists 兜
5815–5818 set st "" / if {[info exists mom_command_status]} / set st [string tolower [string trim $mom_command_status]] 把状态取成小写、去空格的字符串 ① 必须先判存在：没加事件时这个变量不存在，直接读会报错；② string tolower 是因为 NX 真实送进来的是全大写 ACTIVE（这是当初踩过的坑，写 == "Active" 会永远判错）；③ string trim 防手改 .cdl 时带进空格
5820–5822 set ::nc_addvar_on 0 / set ::nc_x_var 0 / set ::nc_y_var 0 先无条件清零（默认不生效） 关键设计：每次事件触发都先复位，避免上一次的残留（例如上一道工序手填过 656）漏到这一次

第 5 章 · 这个实现的逻辑是什么

5.1 状态机：只有三个状态

        ┌──────────────────────────────┐
        │  其它工序：::nc_addvar_on = 0 │  ← 什么也不做（输出逐字不变）
        └──────────────────────────────┘
   工序开始事件（UDE add_variable = Active）
        ↓  PB_CMD_add_variable_flag
        ┌──────────────────────────────┐
        │  本工序：::nc_addvar_on = 1   │  ← 每个 NC 块的 X/Y 被改写
        └──────────────────────────────┘
   工序结束（{End of Path} → PB_CMD_collect_cutting_time 末尾）
        ↓  set ::nc_addvar_on 0
        └──────── 回到状态 0 ──────────┘

为什么用"全局变量 + 两道保险"：
Tcl 里 proc 之间不共享局部变量，而"事件"和"每一行输出"分别在两个 proc 里，
只能用全局变量（:: 前缀）传状态；工序结束再复位，形成闭环。

5.2 判断链：为什么是"黑名单"而不是"白名单"

改写发生在文本层，看到的只是"一行字符串"，所以只能靠行内容特征判断该不该改：

要不要改这一行？
  开关没开？                → 不改（return）
  行是空的？                → 不改
  含 "(" 或 ")"（注释/消息）？→ 不改
  含 G53/G28/G30/G52/G92/G10/G4/G04/G68？ → 不改
  否则                      → 改（把 X/Y 套上 [..+#..]）

用黑名单的理由：

  • 白名单要枚举：.def 里有 90 个含 X/Y 字的块（直线/圆弧/快速/各种循环的各个子块…），
    漏一个就少改一处；而且以后改 .def 又要同步维护。
  • 黑名单只列"X/Y 不是工件坐标"的少数几种情况，稳定得多。
  • 最坏情况是"多改了一行"（例如 G65），而不是"漏改"，且数控程序照样能跑
    —— 失败模式温和。

5.3 改写算法：为什么用 regsub 而不是拆字符串

一行 NC 里，"X" 可能出现多次且含义不同（G53 G0 X0. 里的 X 是机床坐标），
用 split 按空格拆再拼回去，会破坏原有的空格/前导零格式。
regsub 是原地正则替换：

  • 只动匹配到的那一小段（X 后面的数字），其它字符逐字节保留；
  • 用捕获组 \1 把原数字原样搬进去，所以 1.2 还是 1.2、-0.03 还是 -0.03；
  • 返回值天然就是"替换了几处"，顺手当计数器。

而"哪些行不处理"的问题，用前置的 G 码黑名单解决，
不在正则里堆条件 —— 这样规则一目了然，也好维护。

5.4 变量号算法：两级（默认公式 + 手填覆盖）

变量号 = 默认公式（按刀号定位到"每刀 5 格"里的那一格）
         ↓ 若事件里手填了 (>0)
         手填值
  • 默认公式：X = 600 + 刀号*5 - 4、Y = 600 + 刀号*5 - 3。
    这里的 刀号 是还原后的整数刀号（>100 的 刀号*100+补偿号 编码要先还原因）。
  • 之所以"默认就用公式"，是因为这样用户只要加一个事件、什么都不用填就能用；
    手填只是给特殊场合留的口子。

5.5 为什么必须"只改文本、不调输出命令"

PB_CMD_before_output 是被 MOM_before_output 调的 —— 也就是正处在
"输出一个 NC 块"的过程当中。如果在这里再调 MOM_output_literal 之类，
就会递归地再触发一次输出流程，轻则多出行、重则死循环。
所以这一段只做两件事：读 mom_o_buffer、写 mom_o_buffer。
（这也是为什么调试信息放在 A 段之外的事件函数里打印，而不是在这里打。）

5.6 与"需求②（循环 R 值）"共存

同一个 PB_CMD_before_output 里，A 段负责循环 R 值跟踪（需求②），
B 段负责坐标宏（需求③）。两段的先后是确定的：

  1. A 段先跑：它读 mom_o_buffer 里原始的 Z 值来跟踪刀位
    （如果 B 段先改写了 X/Y，虽然不影响 Z，但保持"先跟踪、后改写"的顺序更清晰）；
  2. B 段后跑：改写 X/Y。

A、B 两段互不引用对方的变量（A 用 ::nc_cycR*，B 用 ::nc_addvar_on），所以顺序其实不敏感，
但不要重新排列它们，也不要往 B 段里塞 A 段的逻辑。

5.7 ⚠ 已知缺陷：复位语句可能被跳过（建议修）

PB_CMD_collect_cutting_time 的结构是：

proc PB_CMD_collect_cutting_time { } {
   ...
   if { [info exists ::nc_new_tool_request] } { set ::nc_new_tool_request 0 }   ;# ← 6345
   if { ![info exists mom_tool_number] } { return }                              ;# ← 6347 ★ 提前返回
   ... 累加切削时间 / 记刀号 / 记文本 ...
   if { [info exists ::nc_addvar_on] } { set ::nc_addvar_on 0 }                   ;# ← 6384 复位
}

问题：一旦"本道工序没有 mom_tool_number"，第 6347 行就 return，
第 6384 行的复位永远不会执行 → 开关残留 → 下一道没加事件的工序也会被套上方括号。

风险高不高：实际出程序时 End of Path 几乎总是有刀号（工序都用刀），所以平时看不出来；
但这是一个"迟早会咬人"的隐患。

建议改法（把复位提到 return 之前）：

   # 【需求③】工序结束先关坐标宏开关（必须放在下面那句 return 之前！）
   if { [info exists ::nc_addvar_on] } { set ::nc_addvar_on 0 }

   # 需求①保险：本道工序结束，把"本工序的 set_new_tool 标记"清掉
   if { [info exists ::nc_new_tool_request] } { set ::nc_new_tool_request 0 }

   if { ![info exists mom_tool_number] } { return }

::nc_addvar_on 从 1 → 执行 if { [info exists ::nc_addvar_on] } { set ::nc_addvar_on 0 } → 0 ✅

第 7 章 · 维护、排错、跨机纪律

7.1 三条纪律（老规矩）

  1. 明文母本必须留着（_bf.tcl / .bak84）。加密版 .tcl 绝不能再让 Post Builder 打开并保存
    —— PB 会按 .pui 重写 .tcl，加密当场作废。
  2. 流程固定：PB 里改完 →（如需）降 ni → 加密 → 双击 Deploy-TBC.cmd → 出程序核对 NC。
  3. 跨机四件套一致：.tcl / .def / .cdl / .pui，以及 NX 全局 ude.cdl
    （.cdl 决定"事件有哪些参数"，.pui 决定"事件挂给哪个 proc"）。

7.2 PB 保存后被重写怎么办

在 Post Builder 里改过东西并保存了 → .tcl 里这 4 段会被 PB 重写掉 →
直接再跑一次 Apply-CoordMacro.ps1（桌面，幂等，自动备份）。

powershell -ExecutionPolicy Bypass -File "%USERPROFILE%\Desktop\Apply-CoordMacro.ps1"

跑完看同目录 Apply-CoordMacro.log，最后一行 === DONE === 即成功。

7.3 现场排错表

现象 原因 / 处理
该出方括号的工序，一个都没有 ① 事件没挂上 → 查 .pui 第 777 行登记；② 状态不是 Active → 打开 ::nc_dbg 看 (DBGADD on=..)；③ .cdl 里没有 add_variable 事件定义；④ 没重启 NX 就加事件
方括号有，但号不对（例如出现 +#596） 刀号没取到 → mom_tool_number 在该块不存在，走了 tn=0 的兜底。把那段 NC 发出来核对；或直接在该工序事件里手填变量号
本该没有方括号的工序出现了方括号 复位没执行 → 见第 5.7 节（return 提前返回的缺陷）；或 PB 保存后代码被重写，需重灌
某行 G28/G53 被套了方括号 跳过规则被改动 → 核对第 3.3 节那三行是否与原版一致（尤其 \M 不能丢）
坐标整字消失 说明改写发生在"块定义层"而不是"文本层" → 请确认没有把 _EXPR.def 混进来用
改了 .cdl 后事件框里还是没有变量号格 ① 只改了一个 .cdl（后处理 + NX 全局两个都要改，且要一致）；② 没重启 NX；③ 旧事件要删掉重加

7.4 验收判据（每次改完必查）

① 加事件的工序：G0/G1/G2/G3 + G8x 的 X/Y 都带 [..+#..]，Z/I/J/K/R/F 原样
② 没加事件的工序：与改动前【逐字一致】（这一条是硬指标）
③ G53/G28/G30/G52/G92/G10/G4/G68 行：一个方括号都没有
④ .def 文件的字节数不变（本方案不碰 .def）
⑤ 变量号与刀号对得上：T10 → #646/#647；T7 → #631/#632；T1 → #601/#602
